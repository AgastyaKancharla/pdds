# Competitor Tech Stacks: Frontend/Mobile & Backend Infrastructure

Follow-up to the existing market-research pass (AI/ML models, accuracy claims, monetization, dataset choices — already covered in `Plant diagnosis app market research/`). This file covers the specific gap of **what tech stack each competitor actually runs on**: mobile framework (native vs. cross-platform vs. PWA), offline/on-device capability, and backend/cloud infrastructure, for Plantix, PictureThis/Glority, Plant.id/Kindwise, and Pl@ntNet.

**Research-session constraint:** `WebFetch` failed with DNS resolution errors on every external domain attempted this session (Wikipedia, GitHub, job boards, HAL, recruitee, etc. — same environment/tooling issue noted as a caveat in the earlier `tech_frameworks_apis.md` pass). Where a snippet attributes a direct quote to a primary source (e.g., a Wikipedia page, a job posting, an arXiv paper), that is noted, but none of it was independently re-verified by opening the page directly in this session — treat accordingly and re-fetch directly before high-stakes citation.

## Plantix (PEAT GmbH / Helm AG)

### Takeaway
Plantix's core app is confirmed Android-targeted (per Wikipedia) with no public source confirming whether it (or its iOS counterpart) is native (Kotlin/Swift) or cross-platform. The clearest concrete signal found is a current/recent PEAT job listing for a "Mobile Engineer" on a team called **SKYFLD** (a farm-management product that embeds Plantix's AI) explicitly requiring **Flutter** (Dart) for iOS and Android — but it is not certain this listing describes the core consumer Plantix app itself rather than a sibling/B2B product. A separate backend job listing describes Plantix's core backend as **AWS**-hosted **Python/TypeScript** microservices (Flask, PostgreSQL, MongoDB, Redis, Jenkins, Docker) processing tens of thousands of plant images/day. Plantix's "offline" claim, as far as any source documents, applies to its disease/pest/treatment **reference library**, not to photo-based AI diagnosis itself — the "Health Check" diagnosis flow is described as photo-to-server, with AI analysis happening server-side. No PEAT/Plantix engineering blog, GitHub org, or conference talk was found.

### Cited Findings
- Plantix was launched in 2015 by PEAT GmbH, a Berlin-based AI startup; Wikipedia's summary (returned via search) describes it running on Android and diagnosing plant damage from user-submitted photos — [Plantix — Wikipedia](https://en.wikipedia.org/wiki/Plantix)
- A current/recently-posted PEAT careers listing, "Mobile Engineer (SKYFLD), Germany-based, hybrid," asks for 5+ years mobile engineering experience and Flutter proficiency building iOS and Android apps, with Dart and Google Maps API experience called out on a mirrored listing — [Plantix/PEAT Recruitee listing](https://plantix.recruitee.com/o/mobile-engineer-fmd-skyfld-germany-based-hybrid); mirrored at [Arbeitnow](https://www.arbeitnow.com/jobs/companies/plantix/mobile-engineer-skyfld-germany-based-hybrid-berlin-485594)
- An Austrian agricultural-chamber listing for SKYFLD describes it as a farm-management app that "brings in the Plantix AI" so users can document field observations and pest/deficiency symptoms, with CropX sensor integration — i.e., SKYFLD is a related/B2B product built on top of Plantix's AI, not necessarily the same codebase as the consumer Plantix app — [SKYFLD — noe.lko.at](https://noe.lko.at/skyfld-betriebsmanagement+2400+4089144)
- A (now-closed) remote "Senior Software Engineer" listing for Plantix's **core backend infrastructure** describes a department of software/ML/DevOps engineers building scalable microservices that process tens of thousands of plant images daily, with a named stack of **AWS, Python, TypeScript, Flask, PostgreSQL, MongoDB, Redis, Jenkins, and Docker** (explicitly caveated in the posting as "not set in stone") — [RemoteOK: Senior Software Engineer, Plantix](https://remoteok.io/remote-jobs/106245-remote-senior-software-engineer-plantix)
- A German platform article (reset.org) describes the core "Health Check" diagnosis workflow as: the user photographs a diseased plant and sends it to the **Plantix server** under the "Health Check" menu item, where an AI compares it to known patterns and returns a diagnosis within seconds — implying diagnosis inference is server-side, not on-device — [reset.org: Plantix – The Plant Doctor You Can Fit In Your Pocket](https://en.reset.org/plantix-plant-doctor-your-pocket-06072016/)
- FAO's e-agriculture page and an ICRISAT case-study assessment both describe Plantix's **offline feature** as a library of pest/disease/nutrient-deficiency reference content available without a connection — not as offline photo diagnosis — [FAO e-agriculture: Plantix](https://www.fao.org/e-agriculture/es/node/13281); [ICRISAT: Plant protection application app Plantix](https://issca.icrisat.org/scalable-solutions/plant-protection-application-app-plantix)
- One unofficial AI-tools directory claims the app can be used in "offline mode" to capture images for later upload once connectivity returns — this is a single secondary/unofficial source, not corroborated by Plantix or by the other sources above, and is flagged as lower-confidence — (source not independently re-opened this session)

### Inferences
- Given the backend job posting's detail (AWS, Flask/Python, TypeScript, Postgres/Mongo/Redis, microservices processing tens of thousands of images/day) and the "Health Check" workflow description (photo sent to server, AI analyzes it there), Plantix's primary disease-diagnosis inference most plausibly runs as a server-side API call against a cloud-hosted (AWS) model-serving backend, not an on-device model — the "works offline" claim found in primary-ish sources (FAO, ICRISAT) is best read as "offline reference library, online diagnosis," which is a narrower claim than "offline diagnosis."
- The Flutter/Dart mobile-engineer listing is a meaningful signal that at least part of PEAT's current mobile engineering (SKYFLD, and plausibly Plantix itself if the teams are shared/converged) uses Flutter rather than fully native Kotlin/Swift codebases — but because the listing names SKYFLD specifically and SKYFLD is described elsewhere as a related-but-distinct farm-management product, this should not be stated as confirmed fact for the core Plantix consumer app without a listing that names Plantix directly.

### Gaps
- No Plantix/PEAT engineering blog, public GitHub organization, or conference talk describing architecture was found despite multiple targeted searches.
- Whether the core Plantix consumer app (as opposed to SKYFLD) is Flutter, React Native, or native Kotlin/Swift is not confirmed by any source found — flagged as **not publicly documented**.
- Whether any part of Plantix's disease-diagnosis pipeline runs on-device (e.g., a lightweight TFLite/CoreML pre-filter before a server call) was not confirmed or denied by any source found.
- Plantix's privacy policy pages returned in search only covered the GDPR/controller-identity boilerplate (PEAT GmbH, Berlin); the hosting/international-transfer sections that might name AWS explicitly were not retrieved in the snippets returned.

## PictureThis (Glority)

### Takeaway
This is the least publicly documented of the four. No engineering blog, GitHub org, job listing (English or Chinese-language search), or app teardown was found that confirms PictureThis's mobile framework (native vs. React Native/Flutter) or its cloud backend provider. The only concrete technical signal found is a third-party mobile-security scan (NowSecure) showing the app's network traffic touches `amazon.com` and `google.com` hostnames — a weak, ambiguous signal (consistent with AWS/GCP hosting, but equally consistent with CDN, ad SDKs, Google Play Services, or Firebase/Analytics use, none of which were distinguished in the scan). The app advertises an offline identification feature in at least one store listing, but no technical description (on-device model format, size, architecture) was found.

### Cited Findings
- PictureThis is developed by **Glority Global Group Ltd.** (also rendered "Glority Software Limited" / "Glority LLC" across different storefronts, suggesting a Hong-Kong-registered holding structure with regional subsidiaries) — [Softpedia developer page](https://mobile.softpedia.com/apk/developer/glority-software-limited-1950); [App Store listing](https://apps.apple.com/app/1252497129)
- A NowSecure mobile-app security report on the Android build (`cn.danatech.xingseus`, developer "Glority Global Group Ltd.") documents the app communicating with external hosts including `amazon.com` and `google.com`, and flags collection/sharing of data "often designated as sensitive and private"; the iOS build's report shows a similar pattern — [NowSecure: PictureThis Plant Identifier (Android)](https://www.nowsecure.com/marc-app/picturethis-plant-identifier-android/); [NowSecure: PictureThis Plant Identifier (iOS)](https://www.nowsecure.com/marc-app/picturethis-plant-identifier-ios/)
- A separate "PictureThis - Flora" App Store listing's FAQ states the app offers offline plant identification ("identify plants even without an internet connection") without describing the underlying model/runtime — [appshunter.io: PictureThis - Flora](https://appshunter.io/ios/app/picturethis-flora/id6736628744)
- A peer-reviewed study (PMC) independently testing PictureThis against toxic-plant images found 82% accuracy at genus level but only 64% at species level within a genus — included here only to confirm the app has been externally studied, not as architecture evidence — [PMC8938528](https://pmc.ncbi.nlm.nih.gov/articles/PMC8938528)
- A Glority-branded US patent family exists for "Plant group identification" (e.g., US11823388B2, US12347113B2), confirming Glority has filed its own ML/CV patents rather than relying purely on a third-party vendor model — but these patents concern the identification model/algorithm (already covered by the earlier market-research pass), not infrastructure — [US11823388B2](https://patents.google.com/patent/US11823388); [US12347113B2](https://patents.google.com/patent/US12347113)

### Inferences
- The absence of any public engineering blog, job listing, or conference talk — despite repeated English- and Chinese-language searches — suggests Glority keeps its engineering organization and infrastructure choices non-public, in contrast to Plantix/PEAT (which at least publishes job listings naming its stack) and Pl@ntNet (publicly documented by design, as a research consortium).
- The `amazon.com`/`google.com` network-traffic observation from NowSecure is not strong enough to state "PictureThis runs on AWS" or "PictureThis runs on GCP" as fact — it is equally explainable by common third-party SDKs (ad networks, Firebase/Crashlytics, Google Play services, image CDNs) bundled into almost any consumer app, and should not be cited as confirmed cloud-infrastructure evidence.

### Gaps
- No public source confirms whether PictureThis is built natively (Swift/Kotlin) or cross-platform (React Native/Flutter) — **not publicly documented**.
- No public source confirms Glority's cloud provider (AWS/GCP/Azure/self-hosted) or backend architecture (microservices, serverless, GPU inference servers) — **not publicly documented**.
- No Glority engineering blog, GitHub organization, or job posting describing mobile/backend tooling was found in this pass, in either English or Chinese-language search queries (tried "格微科技", "形色" + 招聘/技术栈).
- The technical mechanism of PictureThis's advertised "offline identification" (on-device TFLite/CoreML model vs. a cached subset of results) is not documented anywhere found.

## Plant.id / Kindwise (plant.health, crop.health)

### Takeaway
Kindwise (Brno, Czech Republic) is structurally different from the other three: its flagship products (Plant.id, plant.health, crop.health, insect.id, mushroom.id) are **REST APIs** meant for integration into third-party software, not a single consumer app with its own dedicated mobile codebase. Where Kindwise does offer an end-user-facing demo of Plant.id, the company's own blog explicitly describes it as a **Progressive Web App (PWA)** — installable to the home screen from a mobile browser on iOS or Android — which is a notably explicit, citable PWA confirmation (rarer among the four companies researched). Kindwise's original consumer app, FlowerChecker (launched 2014, a human-botanist-assisted ID service), was discontinued in October 2024. No public source (job listing, engineering blog, GitHub org, conference talk) describes Kindwise's backend cloud provider or infrastructure stack.

### Cited Findings
- Kindwise is a Brno-based machine learning company; per its Wikipedia entry (returned via search), it was founded in 2014 by PhD students, launched the Plant.id identification API in 2018 and the plant.health disease-identification API in April 2022, and discontinued its original FlowerChecker consumer app in October 2024 after 10 years of operation — [Kindwise — Wikipedia](https://en.wikipedia.org/wiki/Kindwise)
- Kindwise's own "about" page states the company "began as students with a simple idea: a smartphone app for plant identification" (the FlowerChecker app), dated to 2013 in the page's own framing — note this is a one-year discrepancy against Wikipedia's "founded 2014," unresolved in this pass — [Kindwise: About](https://www.kindwise.com/about)
- A Kindwise blog post explicitly describes its **Plant.id web demo as a Progressive Web App**: "a progressive web app that users can install on iOS or Android from the browser," limited to 5 free identifications/week in that free demo, with Kindwise pointing users wanting a full consumer product toward its (now-discontinued) FlowerChecker app — [Kindwise: Use Plant.id Demo As An App](https://www.kindwise.com/post/use-plant-id-demo-as-an-app)
- Plant.id is architected as a stateless REST API: a third-party open-source Flutter app ("Nebat," on GitHub) demonstrates calling Plant.id's REST API from a Flutter client, which is consistent with Plant.id being consumable from any client framework over HTTP rather than requiring a specific SDK/platform — [github.com/babasahi/Nebat](https://github.com/babasahi/Nebat) (third-party integration, not a Kindwise-authored client)

### Inferences
- Because Kindwise's core products are APIs rather than apps, the "frontend framework" question is largely inapplicable to Plant.id/crop.health/plant.health themselves — the relevant architectural fact is that Kindwise explicitly ships at least one of its own user-facing surfaces as a PWA rather than a native or cross-platform-compiled app, which is a deliberate, lower-overhead choice for a small API-first company and is worth noting as a contrast point for a student team evaluating its own frontend choice.
- The complete absence of any backend/cloud job listing or engineering write-up (despite Kindwise clearly running production ML inference at scale, per the dataset/accuracy section of the earlier research pass) suggests Kindwise, like Glority, treats its infrastructure as non-public — this is an absence of evidence, not evidence that it runs on any particular provider.

### Gaps
- No public source names Kindwise's cloud provider (AWS/GCP/Azure) or backend architecture (serverless, containers, GPU inference servers) — **not publicly documented**.
- No Kindwise engineering blog, GitHub organization for its production inference stack, or job posting was found in this pass (searches tried English and Czech-market-adjacent terms).
- The one-year discrepancy between Kindwise's own "about" page (2013) and its Wikipedia entry (founded 2014) on FlowerChecker's origin date was not resolved.

## Pl@ntNet (Inria / CIRAD / INRAE / IRD consortium)

### Takeaway
Pl@ntNet is markedly more openly documented than the three commercial apps, consistent with its public-research origin (the consortium is managed by Inria, with CIRAD, INRAE and IRD as founding members). It publishes a public GitHub organization (datasets, dataloaders, ML research frameworks — though not the production mobile-app source or model weights), and multiple peer-reviewed/preprint papers describe its server-side "Identification Engine" (cloud-hosted, GPU-backed, performance-tuned via thread-pool sizing) handling roughly 400,000 plant-image identification requests/day for 10M+ users as of a 2021 performance-engineering paper. Notably, Pl@ntNet's compute-heavy model **training** runs on French national HPC infrastructure (a GENCI/IDRIS allocation on the Jean Zay supercomputer, per a 2024 paper) rather than commercial cloud GPU instances — a genuine public-research-vs-commercial-cloud contrast point the task asked to look for. An "offline/embedded identification" mode is advertised in store listings, though the technical format of the on-device model was not found. The app is described (in an older, undated record) as having three front-ends — Android, iOS ("being currently re-developed" as of that record), and web.

### Cited Findings
- Pl@ntNet is a joint initiative of Cirad, INRAE, Inria and IRD, with consortium management entrusted to Inria — [INRAE/CIRAD project materials, via search summary] (e.g., [CIRAD: Pl@ntNet, France case study](https://impress-impact-recherche.cirad.fr/ex-post/case-studies/pl-ntnet))
- Pl@ntNet maintains a public GitHub organization (`github.com/plantnet`) hosting, among others: **PlantNet-300K** (the NeurIPS 2021 long-tailed plant-image dataset, BSD-2-Clause), **GeoLifeCLEF** (challenge toolkit, MIT), **malpolon** (a deep species-distribution-modeling framework, MIT), **gbif-dl** (GBIF dataloaders, MIT), and an `ai-taxonomist-webcomponent`; the production mobile apps themselves and the deployed model weights are not published there — [github.com/plantnet](https://github.com/plantnet)
- A 2021 systems paper ("Reproducible Performance Optimization of Complex Applications on the Edge-to-Cloud Continuum") uses Pl@ntNet as its real-world case study and describes the architecture as: users on the edge (mobile app) take photos; the **Pl@ntNet Identification Engine, located in the Cloud**, performs species prediction and similarity search via deep learning; engine performance is strongly dependent on configured thread-pool sizes (GPU thread counts capped by GPU memory); the paper states Pl@ntNet has **more than 10 million users worldwide and processes about 400,000 plant images per day**, and validates its proposed optimization methodology against Pl@ntNet on 42 nodes of the Grid'5000 research testbed — [arXiv:2108.04033](https://arxiv.org/pdf/2108.04033)
- A 2024 paper on Pl@ntNet's cooperative-learning/AI pipeline explicitly credits a **GENCI allocation (A0151011389) for IDRIS HPC resources** — i.e., the Jean Zay national supercomputer — for its compute, alongside ANR funding, rather than naming a commercial cloud GPU provider — [arXiv:2406.03356](https://arxiv.org/pdf/2406.03356)
- A 2018 conference-talk abstract states Pl@ntNet's training set was then ~12 million images across ~275,000 species, that training a CNN at that scale "can take up to several months on a single node equipped with four recent GPUs," and that the team therefore moved training workloads to French national HPC systems — [indico.egi.eu talk abstract](https://indico.egi.eu/event/3973/contributions/9313/contribution.pdf)
- An older record (exact publication date not independently confirmed in this pass) describes Pl@ntNet's back-office as based on the **Snoop visual search engine** (built by the ZENITH research team) and **NewSQL technologies** for data management, and describes the platform as having three main front-ends: an **Android app**, an **iOS app** ("being currently re-developed" as of that record's writing), and a **web version** — (via WebSearch summary of a HAL record; not independently re-opened this session, flagged for direct confirmation)
- Pl@ntNet's public API (`my.plantnet.org`) is a synchronous REST API: clients POST local image files or GET remote image URLs (1–5 images per request) and receive back ranked species + confidence scores; a non-plant image returns a 404 "Species not found" unless a `no-reject` parameter is set — [my.plantnet.org/doc/getting-started/introduction](https://my.plantnet.org/doc/getting-started/introduction)
- A 2018 HAL paper ("An image-based Plant identification platform for thousands of species") describes the service's species coverage growing from ~800 species at its 2009 inception to ~6,000 species of European/Indian Ocean/French Guiana/North African flora by 2018, and a later record states the app was (as of that record) distributed in 180+ countries with 10M downloads and ~20,000 species identifiable — [hal.archives-ouvertes.fr/hal-01837355, summary via search]
- At least one app-store mirror listing explicitly advertises "Offline/embedded identification available!" for the Pl@ntNet app — [pl-ntnet.fileplanet.com/apk](https://pl-ntnet.fileplanet.com/apk)
- A separate, unrelated on-device plant-ID research model ("BoltNet," 2026) is evaluated against the **PlantNet-300K dataset** as a benchmark and is reported as the most accurate sub-2MB model on it — this confirms PlantNet-300K's use as a standard academic benchmark for on-device models generally, but is not evidence about Pl@ntNet's own production offline mode — [BoltNet paper, CVPPA workshop](https://iris.unimo.it/retrieve/3c86500e-4b19-4785-ad62-df2ea02f672b/BoltNet___cvppa.pdf)

### Inferences
- Pl@ntNet's willingness to publish systems-performance papers (arXiv:2108.04033), HPC-funding acknowledgments (arXiv:2406.03356), and a public GitHub org makes it the single most externally-auditable architecture among the four competitors — directly consistent with the task's expectation that a public-research-origin project would be "more open than the commercial apps."
- The explicit mention of Grid'5000 (a French research computing testbed) for performance validation and Jean Zay/GENCI/IDRIS for training compute indicates Pl@ntNet's heavy compute (training, and at least some architecture validation) runs on **public research infrastructure**, not commercial cloud (AWS/GCP/Azure) — a structurally different cost/ops model than a startup would use, and one a small team likely cannot replicate directly, but the "Identification Engine in the Cloud" framing in the 2021 paper leaves open whether production inference serving itself (as opposed to training/validation) runs on research infrastructure or a commercial cloud front end.
- The scale figures across sources are inconsistent in a way that looks like normal growth-over-time rather than contradiction (800 → 6,000 → ~20,000 species; and separately 12M training images / 275K taxonomic entries in a 2018 talk, which is a different, broader "taxa" figure than "identifiable species") — dates should be checked when citing any single number.

### Gaps
- This session could not directly open the HAL records, arXiv PDFs, or GitHub org (WebFetch DNS failures throughout) — all findings above rely on WebSearch-returned snippets/summaries of those primary sources, not a direct read; re-fetch and confirm before treating any individual figure (species counts, user counts, "Snoop"/NewSQL backend claim) as fully settled.
- Whether Pl@ntNet's production **inference serving** (as opposed to model training) runs on a commercial cloud provider, on Inria/CIRAD's own research-institute datacenters, or on a mix, is not stated explicitly in any source found.
- The current (2026) status of "iOS app being currently re-developed" is from an undated/older record and may no longer be accurate.
- No technical detail (model architecture, file format/size, update mechanism) was found for Pl@ntNet's advertised offline/embedded identification mode.
